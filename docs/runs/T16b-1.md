docs/ai-design.md의 '능력 기반 행동' 중 공유 장비 데이터, 능력 태그, 장비 비용, 능력이 여는 행동 후보, 장비 프리셋을 src/Core에 구현한다. 배역 배분과 행동 계약은 다음 run(T16b-2)에서 한다. 이번 run에서 AgentState.Role(Guard / Attacker / Healer)은 그대로 두고 '이번 교전의 배역'으로만 읽는다. Unity 코드는 바꾸지 않는다. 공개 API(World.Add, AgentState, PuppetBrain.GetDecision 등)는 U5가 쓰므로 유지하고, 새 기능은 추가로만 넣는다.

1) 장비 정의(플레이어·인형·봇이 공유하는 데이터): EquipmentDefinition { Id(문자열), Slot(Weapon | Armor | StageTool), 무기면 RangeBand(Melee | Mid | Ranged), 제공하는 능력 태그 목록, 비용 } 을 둔다. 능력 태그는 열거형 CapabilityTag { Block, Protect, Heal, Disrupt } 이다. 비용은 두 가지만 둔다: MoveSpeedScale(이동 속도 배율, 0 초과 1 이하, 기본 1)과 ImmobileWhileUsing(이 장비의 능력 행동을 하는 동안 이동 불가, 기본 false). ImmobileWhileUsing은 이번 run에서는 데이터와 검증만 하고, 해당 행동(회복·교란)이 생기는 T16b-3에서 적용한다. 공격 특성은 T16d에서 넣으므로 이번에는 두지 않는다.
2) 사거리 대역 → 공격 거리: Melee = 기존 PuppetSettings.AttackRange(기본 2m), Mid = MidAttackRange(기본 3.5m), Ranged = RangedAttackRange(기본 8m). 값은 설정에 둔다.
3) 기본 장비 카탈로그(코드로 정의, id로 찾음): weapon.melee(Melee), weapon.short(Melee), weapon.spear(Mid), weapon.bow(Ranged), armor.shield(Block, Protect, MoveSpeedScale 1), armor.heavyShield(Block, Protect, MoveSpeedScale 0.8), tool.mender(Heal, ImmobileWhileUsing), tool.jammer(Disrupt, ImmobileWhileUsing). 수치는 임의로 정한 값임을 표시한다.
4) 장비 구성(Loadout): 무기 정확히 1개, 방어구 0~1개, 무대 도구 0~1개. 능력 태그는 장비들의 합집합이고 최대 3개다(docs/ai-design.md "개체 하나는 태그 2~3개"). 공격 거리는 무기의 사거리 대역에서, 이동 속도 배율은 장비 비용들의 곱에서 나온다. 무기가 없거나 둘 이상, 같은 슬롯 중복, 없는 id, 태그 4개 이상, 잘못된 비용 값은 결과값으로 거부한다(예외 아님).
5) 장비 프리셋(역할 표를 장비로 옮긴 회귀 기준): 방패형 = weapon.melee + armor.shield(Block, Protect), 근접형 = weapon.melee, 회복형 = weapon.short + tool.mender(Heal). 비용은 모두 1이라 이동이 예전과 같다.
6) World에 장비 구성을 붙이는 방법을 추가한다: World.Add의 새 오버로드나 별도 설정 메서드로 개체마다 Loadout을 줄 수 있고, 개체의 능력 태그·공격 거리·이동 속도 배율을 읽을 수 있다. 플레이어 편 개체도 Loadout을 가질 수 있다(공유 데이터, 이번에는 읽기만 하고 판단에는 쓰지 않는다). AgentState의 생성자와 속성은 바꾸지 않는다. 인형 편 개체에 Loadout을 주지 않으면 Role에 맞는 프리셋을 쓴다(Guard → 방패형, Attacker → 근접형, Healer → 회복형). 그래서 기존 호출 코드(Unity, Core.Sim, 테스트)는 그대로 예전처럼 동작한다.
7) 능력이 여는 행동 후보: 행동 후보를 만들 때 '능력이 있는가?'를 먼저 본다. intercept(막아서기)는 Protect 태그가 있을 때만 후보가 된다. 태그가 없으면 후보 목록에 넣지 않거나 적합도가 항상 0이어야 하며, 역할 가중치·블랙보드 의도·장력·끌림 어떤 값도 이것을 바꾸지 못한다. 나머지 기존 행동(approach, attack, hold, spread, keepDistance, waver)은 능력이 필요 없는 기본 행동이다. 역할 가중치 표와 '<역할>:<행동>' 의도 키는 그대로 쓴다(T16b-2에서 배역 계약으로 바뀐다).
8) 공격 거리와 이동 속도: attack 적합도, approach의 목표 지점(공격 거리 - AttackArrivalMargin), 공격 대상 판정에서 전역 AttackRange 대신 그 개체의 공격 거리를 쓴다. 이동할 때 그 개체의 이동 속도 배율을 곱한다(자세가 무너졌을 때의 PostureSlowScale과는 곱으로 함께 적용). KeepDistance의 KeepMin·KeepMax와 위협 반경은 그대로 둔다.
9) 표시용 노출: 개체별 장비 id, 능력 태그, 공격 거리, 이동 속도 배율을 읽을 수 있게 한다(F1 오버레이용, Unity 연결은 다음에).
10) 시뮬레이션: src/Core.Sim의 --puppets에 --loadout <presets|mixed> 옵션을 더한다. presets = 지금과 같음(기본값). mixed = 앞의 Guard 둘 중 하나는 weapon.melee + armor.heavyShield, 다른 하나는 weapon.melee만(Protect 없음), Attacker는 weapon.spear, Healer는 회복형. 출력 머리에 개체별 장비와 능력 태그, 공격 거리, 이동 속도 배율을 적는다. 기존 금지 패턴 지표 출력은 유지한다.
수치는 설정 타입이나 카탈로그에 두고 임의로 정한 값임을 표시한다.
테스트: (a) 회귀: Loadout을 주지 않은 경우와 프리셋을 명시한 경우의 --puppets 네 시나리오(approach, circle, retreat, healer) 궤적(tick별 위치와 행동)이 같다. 기존 PuppetContract·PuppetBrain·Tension·IntentionBlend 테스트는 수정 없이 통과한다(수정이 필요하면 왜인지 기존 동작 변경 섹션에 적는다). (b) 능력 필터: Guard 배역이지만 Protect가 없는 개체는 무대 구성이 GuardHealer이고 힐러 위협 사실이 있어도, 블랙보드에 'Guard:intercept' 의도가 있어도, 장력이 1이든 0.5든 intercept를 고르지 않는다. 그리고 위협 반경 안에 사람이 있을 때 1초 넘게 이동도 공격도 하지 않는 일이 없다(다가가거나 공격한다). 같은 상황에서 Protect가 있는 개체는 지금처럼 막아선다. (c) 공격 거리: weapon.spear 개체는 사람과 3.5m 이내(2m 초과)에서 attack을 고르고 그 거리 밖에서 멈춰 다가오지 않는다. weapon.bow 개체는 8m 이내에서 attack을 고른다. 경계(정확히 3.5m, 3.5001m)를 포함한다. (d) 비용: armor.heavyShield 개체는 같은 tick 동안 0.8배만 이동한다. 자세가 무너졌으면 0.8 × PostureSlowScale. (e) 검증: 무기 0개, 무기 2개, 같은 슬롯 중복, 없는 id, 태그 4개(예: 테스트 전용 장비로), MoveSpeedScale 0·1.5·NaN은 거부된다. (f) 공유: 플레이어 편 개체에 Loadout을 붙이고 능력 태그를 읽을 수 있으며, 인형의 판단 결과는 플레이어의 Loadout 유무와 관계없이 같다. (g) 결정론: 같은 시드·입력·장비면 같은 궤적. 규칙 코어 테스트는 계속 통과해야 한다.
마지막 메시지에 dotnet run --project src/Core.Sim -- --puppets healer --loadout mixed 출력의 머리(장비 표)와 금지 패턴 지표, 그리고 Protect가 없는 Guard가 실제로 무엇을 했는지 짧게 적는다.

## 리뷰 포인트
- AgentState의 생성자와 속성, World.Add 기존 시그니처가 diff에서 바뀌지 않았는지(추가만 있는지)
- 회귀 테스트 (a)가 Loadout 없음과 프리셋 명시의 궤적을 실제로 비교하는지
- intercept가 Protect 없이는 어떤 경로(의도, 장력, 끌림)로도 나오지 않는지 — 테스트 (b)가 세 경로를 다 건드리는지
- 공격 거리가 전역 AttackRange 대신 개체 값으로 바뀐 곳이 세 군데(attack 적합도, approach 목표, 공격 대상) 모두인지
- ImmobileWhileUsing이 이번에는 데이터·검증만 있고 행동에는 아직 쓰이지 않는지(가정 섹션에 적혀 있는지)
- --loadout mixed 출력에서 Protect 없는 Guard가 멈추지 않고 다가가거나 공격하는지
